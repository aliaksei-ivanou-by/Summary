## Project Deep Dive 1 - Embedded SIP Desk Phone Platform (10 Minutes)

The project I would choose for a detailed discussion is the embedded SIP/IP desk phone platform that I worked on from May 2025 to August 2026. The customer was a network-connectivity equipment manufacturer - switches, routers, PBX systems and SIP telephony, built in its own production facility - and the product was a business desk phone for managed office telephony. That portfolio matters for the engineering: interoperability with third-party and legacy SIP hardware was a constant requirement rather than an afterthought. In practice, that means a physical phone used in offices, reception areas, meeting rooms or dispatcher-like scenarios, where administrators need to configure many devices in a consistent way.

It was a full device software stack, not one standalone application. The main parts were the C++/Qt phone application on the device, Linphone SDK/liblinphone customized for the product, embedded Linux firmware, startup and runtime services, hardware integration, firmware packaging, a device configuration interface, and a Windows tool used to prepare and distribute phone configuration. Linphone is a third-party VoIP/SIP library that handles SIP accounts, registration, calls and media behavior. My primary area was the embedded Qt application, but in practice I worked across telephony behavior, generated configuration, firmware integration, Windows tooling, runtime setup and physical-device debugging.

The technology choices were mostly inherited. The phone application was already based on Qt 5 Widgets, the firmware was already built with Yocto, and the provisioning tool was already a Windows/.NET desktop tool. My task was not to replatform everything, but to make the product work reliably inside those constraints.

The first major subsystem was the embedded Qt phone application. It was the user-facing part of the phone, but also the coordination layer between user actions, telephony state, configuration files, Linux runtime state, network state and hardware. I worked on application structure, models and controllers for accounts, calls, contacts, phonebooks, settings and runtime state. I also worked on call screens, call controls, call lists, registration state and mapping asynchronous telephony events into stable UI behavior.

A typical example is call handling. When a user starts a call, transfers it, switches to video or enters a conference flow, the visible result depends on several things at the same time: the UI state, selected account, Linphone SDK state, SIP signaling, media negotiation, generated configuration and sometimes network conditions. My work was to make those transitions predictable from the user point of view and easier to reason about in code.

I also worked on contacts, phonebooks, call history, programmable keys and device settings. For contacts, the work included local and remote phonebook behavior, import/export flows, refresh behavior, conflict handling and linkage with call history. For programmable keys, the difficult part was keeping configured key targets, subscription state, server notifications and UI indicators consistent. For settings, I worked around network, display, audio, camera, account, certificate and provisioning-related screens and models. Some parts also touched hardware-related behavior on the target device.

The WebRTC video-conferencing path connected the native C++/Qt phone client to a mediasoup-based server application written in JavaScript and running on Node.js. I contributed to the initial server code. The server was later reworked, and my understanding is that the later version used mediasoup-demo. My server-side contribution was to the early implementation. My phone-side integration work included joining conferences, handling participant and media events, updating application state and debugging conference behavior on the device. This gave me experience with both early JavaScript server development and C++ client integration.

The second major subsystem was customized Linphone SDK/liblinphone integration. One of my strongest implementation areas was primary/backup SIP server behavior. In simple terms, the phone needed to recover if the main SIP server became unavailable, switch to a backup server when required, and later return to the main server when it was available again. This was not just adding one backup-server field. The product had to track which server was active, when a switch happened, when recovery should be attempted, and which authentication data belonged to the currently active server.

That work touched the Linphone SDK layer, the Qt application and the provisioning tool. On the SDK side, I implemented the watchdog and failover/failback state machine around account configuration, registration state and active-server state, together with the API used by the application. On the application side, the account models and UI had to show the same state the phone was actually using. On the provisioning side, generated configuration had to include primary and backup server data in a format the device could apply. A registration failure after switching to backup could be caused by generated config, wrong active-server state, wrong authentication data, routing, transport settings, server behavior or network conditions, so debugging required checking the full path.

The third subsystem was the Windows Autoprovisioning Manager. This was a desktop tool for installers and IT administrators. A foundation already existed, but I finished it and built out most of the practical functionality: device discovery, account setup, backup-server settings, contacts, programmable keys, network settings, configuration generation, archives, network-based delivery of generated files, device querying, diagnostics, localization and installer packaging.

I also worked on migrating and modernizing that tool from an old .NET Framework setup to .NET 8 for Windows. The main problem was saved project compatibility. The UI itself did not need to be redesigned, but saved projects could restore incomplete state when fields were added or changed. That is dangerous for this type of tool because the user may not notice the missing value immediately. The problem can appear later on the phone as a broken account, broken backup-server setting, wrong contact data or incorrect provisioning output.

My fix was to make project save/load more explicit. Instead of relying mainly on generic UI-control serialization, the tool used a clear project-state model, saved it as structured data, protected it in the project file, and restored the UI through explicit gather/restore logic. I also had to keep generated configuration stable: account settings, backup-server fields, HA1 password-hash mode, file names, archive layout and per-device output. HA1 is a SIP Digest hash calculated from username, authentication realm and password; if one of those values is wrong, the generated configuration can look valid but the phone may fail to register. I implemented and debugged the HA1 and realm functionality, but the selectable HA1 mode was disabled from release 2.10.1 through the available project-end release history. The current internal project scope moved to ten SIP accounts, but I would not present that as a public product specification.

The fourth subsystem was embedded Linux and firmware integration. Yocto was the inherited build system, and it was suitable because the firmware image had to include the board-support stack, Qt runtime, Linphone SDK, media libraries, configuration files, certificates, fonts, sounds, scripts, services and model-specific files. My contribution was using and adapting that platform for application, SDK, runtime-service and image integration: recipes, installed file layouts, service definitions, startup order, packaging and validation on target devices.

Some defects looked like application bugs but were actually runtime or firmware-composition problems. For example, the application could start before a required service was ready, a file could be missing from the image, a path could differ from the development setup, a media device could appear later than expected, or a network setting could apply in the UI but not survive reboot. These cases required reading target logs, checking installed files and services, validating startup order and testing the complete firmware behavior on the phone.

Testing and debugging were mostly scenario-based. I used focused automated tests where they made sense for local logic, but the final validation required physical devices. A typical investigation started from a QA or customer report with logs, firmware version, device model, SIP server configuration and provisioning state. Then I recreated the scenario, built the relevant component or firmware image, deployed it to the phone, reproduced the issue, collected logs and generated configuration, and narrowed the problem down to the failing layer.

The most difficult bugs were cross-layer. One example was registration working on the primary SIP server but failing after switching to backup. Another example was a saved project opening successfully but restoring incomplete state, which later looked like a phone-side configuration bug. Programmable-key issues were similar: the final visible state depended on configuration, account state, server notifications and UI model updates.

So the value of the project was that it required system-level engineering, not isolated feature work. My strongest contributions were the embedded Qt application and state-model work, implementation of project-specific primary/backup SIP watchdog and failover/failback behavior in the Linphone SDK plus its application integration, major Autoprovisioning Manager functionality, and debugging across SIP behavior, provisioning, embedded Linux, firmware packaging and real hardware.

## Project Deep Dive 2 - Integrated Library System (10 Minutes)

If the role is about long-lived production systems, legacy C or debugging across components, the project I would describe in detail is the integrated library system I worked on from March 2022 to April 2024. The customer was a library-software vendor whose platform serves 9,000+ libraries worldwide. I worked on the platform through EPAM, in direct collaboration with the customer's own developers. An integrated library system is the operational software a library runs on: circulation, cataloging, acquisitions, serials, electronic-resource management and integrations with discovery and self-service systems. Its users are library staff, and its customers are academic, public, national and consortium libraries.

I joined an established product team responsible for ongoing development and maintenance, not a new implementation. On the EPAM side there were three C developers, three Java developers, four QA engineers, a business analyst and a PM who also acted as Scrum Master. On the customer side there were three developers, later four, their development manager and a Product Owner.

The architecture is the thing that makes this project worth discussing. The platform is not one application. There is a C89 backend carrying the core domain behavior, Java data services that mediate database access, a Java desktop application used by staff, and Scala API services that expose functionality externally through a REST API documented in Swagger. PostgreSQL holds most operational data after an earlier migration, while some less-used models still live in MySQL. The components communicate partly through custom inter-service protocols. So a single user-visible operation can cross several processes and several language runtimes before it produces a result.

My primary responsibility was the C89 backend, shared with the other two C developers. C89 means the 1989 C standard, so this is a codebase that has been accumulating compatibility requirements for decades. I implemented new behavior, fixed defects and refactored modules, always with the constraint that established library workflows had to keep working exactly as before. The practical method in code like that is to reconstruct ownership and data flow before touching anything, because fixed-size buffers amplify small mistakes in length, termination and initialization into crashes and corrupted output.

My secondary contributions crossed the language boundaries. I added an API request in Scala, exposed it through Swagger and connected it to established C-side data processing, which meant keeping request mapping, return values and error semantics coherent across two runtimes and the documentation at the same time. I updated Swagger documentation in other tasks. On the Java side I added functionality and fixed defects when a task crossed the backend boundary, including adding a new column to a table in the Java desktop application where the data behind it was prepared on the C side.

The diagnostic style is what I would emphasize. The symptom almost never appeared where the cause lived. A user would see something wrong in the Java desktop application or through the Scala API, and the root cause would be in C, in a data service, in a protocol payload or in runtime state. So the method was log-first: correlate logs across the request path, add focused logging where the existing evidence was insufficient, and only then decide which component owned the fix. For native failures - crashes, invalid memory access - I used SSH, gdb and core dumps on the AWS Linux machines, since compilation and realistic validation happened there rather than locally.

I can give concrete examples of the defects, because they are unusually varied. One was a time-handling defect that would have broken behavior at the upcoming US daylight-saving transition; the root cause was an increment placed at the wrong point in the control flow of a C function, and moving it to the correct position restored the transition behavior. Another class was fixed-size character arrays with length, bounds or initialization problems, which surfaced as truncated text on web pages in some cases and as crashes from invalid or uninitialized memory in others. Another was the product's custom locale and character-mapping system emitting raw encoded characters instead of the intended text. Another was ideographic search and highlighting: the C-side matching applied word-oriented boundaries to Japanese text, which is composed and searched in character and syllable units rather than in whitespace-delimited words, so the fix had to restore correct Japanese matching while preserving the existing Chinese and Korean behavior. And another was blank pages and incorrect page transitions in web and PDF output generated on the C side.

The process was two-week sprints with daily stand-ups, weekly grooming, sprint demos, retrospectives and technical sessions with the customer's developers. Jira tracked the work, Bitbucket hosted the source and Jenkins built on AWS Linux. Builds deployed automatically at night, or on demand through an internal board, to separate developer and QA machines. Every added reviewer, on both the EPAM and the customer side, had to approve a change before it went in. Product releases happened roughly twice a year, which is a very different rhythm from continuous delivery and changes how you think about risk: a mistake that ships has months to affect customers before the next release.

Two things about my own position are worth stating plainly, because interviewers ask. First, I was one of the two or three C developers doing the group's feature work - I took my own tasks through to whichever components a feature touched, but I did not lead the development. Second, this project spans a change in my own status twice over: I joined EPAM at Junior grade in September 2021, was promoted to middle in May 2022, two months into this assignment, and in August 2022 relocated from EPAM Belarus to EPAM Poland. The relocation did not interrupt the work at all - same customer, same codebase, same team; only the employing entity and my location changed. Over the two years I delivered at least twelve features and a much larger number of defect fixes.

Working in C89 has a rhythm that is worth describing because it is genuinely different. There are no containers, no strings, no RAII and no destructors doing cleanup for you. Every buffer has a size someone chose decades ago, and the caller and callee have an unwritten agreement about who allocates, who frees, and how long a pointer stays valid. So the first hour on a defect is almost never spent writing: it is spent reconstructing that agreement from the code, because a change that looks locally correct can violate an assumption three call levels away. The compensating discipline is to make the smallest change that fixes the actual cause, and to be able to explain why it cannot affect anything else.

The release cadence shaped risk differently from anything I had done before or since. With two scheduled releases a year, a defect that shipped could remain until the next scheduled release unless a hotfix was approved, in a system libraries depend on to open in the morning. That is why every change needed approval from every added reviewer on both sides, and why I got used to writing down not just what I changed but what I had checked would still behave the same way.

What I take from that project is the ability to work safely in code much older than the people maintaining it, and to follow a failure across component and language boundaries rather than assuming the component that reported it is the one that caused it.

## Project Deep Dive 3 - Oil and Gas Corporate System (10 Minutes)

If the role is about modern C++ in an enterprise setting, or about data correctness across layers, I would describe the oil-and-gas corporate system I worked on at EPAM from October to December 2021. The customer was a Fortune 500 oilfield-services company operating in 120+ countries, developing technology and digital systems for energy operations, including systems that collect, manage and analyze large volumes of operational data.

The product processed industrial sensor data. Measurements from sensors and upstream acquisition systems arrived, C++17 code parsed and analyzed them, the results were stored in MySQL, and JavaScript integrated into the product codebase exposed the data through the user-facing workflows. The whole thing ran in Microsoft Azure. The EPAM development team was five C++ engineers, a separate QA organization in India handled functional and regression testing, and the customer representatives were in the United States.

My primary area was C++17. I implemented customer-requested functionality, fixed defects, simplified complicated inherited logic and removed obsolete components. I also changed JavaScript when a feature or defect crossed the boundary between backend processing and what the user actually saw, because leaving one side of that boundary corrected and the other side not is how you get a partially fixed system that looks worse than before.

The engineering theme I would draw out is that a single measurement existed in several forms at once: as incoming data, as parsed C++ state, as a calculated value, as a database record, and as something displayed to a user. A visible defect could originate at any of those points. So debugging meant reproducing the user-visible problem with representative input, tracing the affected value through the C++ processing, inspecting the corresponding MySQL state when persistence was involved, and checking the JavaScript behavior when the symptom showed in the user-facing layer - then applying the correction at whichever layer actually owned the faulty behavior, not the one where it was noticed.

It is worth being clear about where I was in my own career at that point. I had joined EPAM in September 2021 at Junior grade, spent the first weeks on onboarding, and this was my first commercial project there. So the assignment was as much about proving I could operate inside a real enterprise codebase as it was about the features themselves. Over the three months I delivered at least four customer-requested features, along with defect fixes and cleanup work.

The sensor-data path is what makes the domain interesting rather than the industry label. An incoming measurement existed as raw input, parsed C++ state, a calculated value, a MySQL record and finally a value exposed through the user-facing workflow. My work was to keep those representations consistent. A defect at one boundary could propagate through the rest of the chain and appear to the user far from its actual cause.

The MySQL side was application-level integration rather than database administration. When persistence was involved, I inspected the corresponding database state and checked that stored and retrieved values remained consistent with the C++ processing and the JavaScript-facing workflow. I do not present this as ownership of schema design or database performance tuning.

Simplifying inherited logic deserves a sentence, because it is easy to say and easy to do badly. The code had accumulated layers: conditions that could no longer be true, branches kept for a configuration that no longer existed, helpers duplicated with small differences. The rule I worked to was that a simplification has to be provably behavior-preserving before it is worth anything - which in practice means understanding why the dead branch was written before deleting it, because sometimes it is not dead. Removing obsolete components was the same discipline applied at a larger scale.

The whole system ran in Microsoft Azure, which mattered mostly in that the environment I reasoned about was not the one on my machine. The team was five C++ engineers at EPAM, functional and regression testing sat with a separate QA organization in India, and the customer representatives were in the United States. That spread has a practical consequence: a question asked at the end of my day is answered at the end of theirs, so a report that is ambiguous costs a full day rather than five minutes. I learned to write reproduction steps and expected behavior the way you would write them for someone you cannot interrupt.

A concrete shape of the work helps here. A typical task started as a report that a number shown to a user was wrong, or that a workflow produced nothing where it should have produced a result. The first job was to get representative input that reproduced it. Then I would follow the value: what the parser built from the raw measurement, what the calculation did with it, what was actually written to MySQL, and what the JavaScript layer displayed. Each of those is a place the value can change, and each looks innocent in isolation. The fix goes at the layer that actually owned the wrong behavior, which is regularly not the layer where it was noticed.

Crossing into the JavaScript side was a deliberate choice rather than scope creep. If a defect spans the boundary between backend processing and what the user sees, correcting one side and leaving the other produces a system that is partially fixed and harder to reason about than it was before - the backend now behaves one way and the interface still describes the old behavior. So I changed both sides when the feature or defect genuinely crossed, and kept the change reviewable by keeping it narrow.

The other thing worth mentioning is that this was a three-month assignment, which shaped everything. There was no time for architectural replacement, so the value came from becoming productive quickly in unfamiliar commercial C++ code, making focused and reviewable changes inside the existing architecture, and leaving clear reproduction steps and expected behavior for a QA organization in a different country and time zone. If an interviewer wants the honest summary: this was the project where I stopped being someone who had learned C++ and became someone who worked in it.

## Project Deep Dive 4 - Satellite and UAV Optical Imaging (10 Minutes)

If the role needs algorithmic depth, R&D experience, or design under hard resource constraints, the period I would describe is my more than seven years at PELENG, from August 2012 to January 2020. I spent all of it in the same unit - the research department of the Space Research and Design Division - as a design engineer - which in practice meant algorithm developer.

PELENG develops and manufactures optical and optoelectronic systems, and its public space product line includes optoelectronic imaging equipment, star sensors and astro-orientation systems. In other words, the company builds the cameras that fly on Earth remote-sensing satellites. Public sources credit it with the imaging payloads of the Kanopus-V series and the Belarusian spacecraft BKA, and with EgyptSat-2. Over my period the organization's instruments were involved in those programs plus EgyptSat-A, and in programs such as Obzor-O, Monitoring-SG and Meteor-MP, alongside an optical system for unmanned aerial vehicles.

My work was image-processing algorithms for those instruments, almost entirely in MATLAB, across six main projects.

The first, from 2012 to 2013, was frame stitching. A high-resolution satellite imager does not have one detector - its focal plane is assembled from several detector arrays, so a frame arrives as separate segments. Joining them turned out to be two problems, not one. The geometric part used feature-based alignment with keypoint matching in the overlap region rather than the nominal design positions, because the real offset differs from the design value and drifts with thermal and mechanical conditions. But correcting the geometry made a second problem more visible rather than less: two physically different detectors respond differently to the same radiance, so a geometrically perfect join still shows a brightness step unless the radiometric difference is matched across the seam.

The second, from 2013 to 2014, was onboard lossy compression - an algorithm of the ADPCM family, adaptive differential pulse-code modulation, reaching a 3 to 4 times compression ratio. This is the project I would use if the interviewer wants to talk about engineering judgement, because the interesting part is that I deliberately chose a weaker algorithm. Transform-based codecs achieve better quality per bit, and they did not fit the onboard computation budget. Differential predictive coding is cheap - a prediction, a subtraction and a quantization step per sample, no transform, no large buffers - and cheapness was the binding constraint on radiation-tolerant hardware that is deliberately generations behind ground equipment. So the design effort went into the predictor and the quantization adaptation within that cheap family, rather than into reaching for a family the hardware could not afford.

The third, from 2014, followed directly from that. The compression ratio was fixed by the downlink budget, so instead of pushing the ratio I worked on improving the quality delivered at the existing ratio, by predicting the image type and adapting quantization to it. Remote-sensing scenes vary enormously - open water, uniform agriculture, forest, urban texture, cloud - and they distribute the cost of quantization error very differently, so classifying the content gets more usable image out of the same bits.

The fourth, from 2014 to 2016, was software to determine the linear ground resolution actually achieved in an image. That had been a manual, expert-driven analysis performed on flight-test imagery, which made it slow and dependent on who performed it. The hard part was not the code: it was agreeing on a criterion precise enough to encode, because resolution is one of the headline specifications an instrument is accepted against, so the resulting number has to be defensible. Once that was settled, the measurement became repeatable and fast, and flight-test analysis stopped being a bottleneck.

The fifth, running in parallel from 2015 to 2016, was different in character - a database of remote-sensing satellites and their parameters, built on Ruby on Rails and PostgreSQL with a web interface. Mission, platform, instrument, spectral band and orbital parameters have a natural relational structure that spreadsheets flatten and lose. It was also my first substantial work with relational modelling and web development.

The sixth, in 2018, extended the work to an optical system for unmanned aerial vehicles: debayering, image format conversion, stabilization and frame fusion modules. Debayering reconstructs full colour from a Bayer colour-filter array, where the difficulty is at edges, since naive interpolation invents colour fringes exactly where the image carries most information. I also developed the module that computes the coordinates of the frame centre and calibrated the inertial measurement unit against the camera. That last one is a good story: the coordinates were wrong while the camera worked correctly and the navigation board worked correctly, because the error was a small boresight misalignment living entirely in the relationship between them - invisible to any test that exercises either subsystem alone, and large on the ground at operating altitude.

Alongside those projects I worked on radiometric correction coefficients for the detector arrays, participated in aligning image sensors in a common plane, planned imaging for flight tests using Systems Tool Kit, produced formal design documentation, and took part in flight testing - more than thirty UAV test flights as payload operator, and satellite in-orbit testing and operation control.

Two of those deserve more than a mention. Radiometric correction is the layer everything else stands on: detector arrays are not uniform, each element has its own gain and offset, and without correction those differences appear as fixed patterns - stripes, blotches - that no later processing can distinguish from real ground detail. Deriving and applying the coefficients is unglamorous work whose whole value is that nothing downstream has to think about it. The other is IMU calibration on the UAV system, computing the alignment between the inertial unit and the camera and from it the geographic coordinates of each frame centre. That one taught me a lesson I still use: the imagery looked correct and the navigation data looked correct, and the coordinates were wrong, because the error lived in the relationship between two subsystems that were each individually fine. Nothing in either subsystem's own output can reveal that.

There is also a handover that shaped how I wrote algorithms. I developed in MATLAB, but an onboard compression algorithm has to run as flight software on constrained hardware, implemented by a different group. So the deliverable was never just a working script: it was a specification precise enough that someone else could reimplement it and get comparable results, plus the reference data to prove they had. Anything I left implicit - a rounding convention, an edge case at a frame boundary, the order of two operations - became a discrepancy for someone else to chase.

Flight testing is worth describing because it is where the feedback loop actually closed. Operating the payload on a UAV campaign means seeing the instrument behave in real conditions rather than reading a dataset afterwards: how imagery degrades with light, angle, vibration and atmosphere, and how much of what you assumed in the algorithm was an assumption. Those opportunities were scarce and expensive, which is exactly why automating the resolution assessment mattered so much - it turned a slow expert judgement made on limited flight-test material into a number anyone could reproduce.

Two constraints defined this whole period, and they are what I would want an interviewer to take away. The first is the onboard computation budget, which makes the best algorithm on paper worthless if it cannot run where it has to run. The second is irreversibility: lossy compression discards information permanently, and an onboard algorithm cannot be revised after launch. There is no staged rollout, no A/B test in production and no hotfix. That is a different standard of verification from anything in ordinary software, and it is the discipline I carried into embedded work later.

## Project Deep Dive 5 - Industrial 3D Scanning and Metrology (10 Minutes)

If the conversation is about computer vision, 3D data or my transition into commercial C++, I would describe my work at RIFTEK from March to May 2020. It was short, three months, and it was my first commercial C++ role after more than seven years of MATLAB algorithm work.

RIFTEK develops and manufactures optoelectronic instruments for measuring geometrical quantities - laser triangulation sensors, 2D laser profile scanners and machine-vision systems. A 2D laser profile scanner projects a laser line onto an object and returns the profile of that line, which is a cross-section rather than a volume. The research question I worked on was: given several of the company's standard production scanners observing the same object from different positions, can you produce one consistent 3D model?

I built a C++17 desktop application on Qt that did exactly that. It acquired or loaded profile data from multiple sensors, transformed each sensor's profiles from its own local coordinate system into a shared 3D frame using the known mounting geometry, accumulated the result as a point cloud, and then applied Point Cloud Library operations - filtering, voxel downsampling, outlier removal, normal estimation, alignment refinement and surface reconstruction - to turn the accumulated points into a usable model. I used Open3D alongside PCL for comparison and visualization, so the library choice rested on measured behavior on real datasets rather than on preference.

The hardest part was error propagation from sensor pose. Every point's 3D position depends on an externally supplied pose, and a small angular error there is invisible in the input and unmistakable in the output - it appears as doubled or smeared surfaces where two sensors' coverage overlaps. That led to two decisions I would defend. First, the overlap regions are the diagnostic: where two sensors see the same surface they must agree, and any disagreement quantifies the pose error rather than merely indicating one. Second, the known mounting geometry stayed as the primary transformation with cloud registration only as refinement, because letting a registration algorithm silently absorb a real geometric error produces a self-consistent cloud that no longer means anything in absolute terms. On a measurement product, that is the difference between a model and a measurement.

The same logic shaped the filtering. Stronger smoothing and coarser downsampling almost always make a point cloud look better while making it mean less, which on a metrology product is exactly the wrong trade unless it is made deliberately. So I checked results against objects of known geometry rather than against how the render looked.

The Qt application deserves its own explanation, because its purpose was not presentation. Algorithm code that only its author can run is worth very little inside a company: the people who need to judge whether a reconstruction is good enough are the measurement engineers, not the person who wrote the filter. So the application was built around loading recorded datasets, running and inspecting individual pipeline stages, viewing clouds and models in three dimensions, and exporting results - designed for fault localization rather than around a single end-to-end button.

I restructured the application early on so that each pipeline stage could be run and viewed independently, and individual sensors included or excluded. That was the single most useful change in the project: it turned "the model looks wrong" into "sensor 2's contribution is offset after transformation", and it let other engineers reach that conclusion without me.

Choosing the reconstruction approach was the other substantial piece. There was no established in-house answer to which library or method suited this data, so I implemented surface reconstruction on the processed cloud and evaluated Point Cloud Library against Open3D on real recorded datasets rather than on examples. The differences that mattered showed up only at the edges - incomplete coverage, thin features, surfaces at oblique angles to the laser line - because on well-covered regions almost any reasonable method produces something acceptable. The outcome was a comparison based on evidence from the company's own data instead of a preference, which is the more useful thing to hand to a team that has to live with the choice.

One limit was physical rather than algorithmic, and recognising that early saved time. A laser line reaches what it reaches: undercuts, steep angles and shadowed regions return no data at all, and no reconstruction algorithm can invent it. It can interpolate plausibly, which on a measurement product is the wrong answer delivered convincingly. So a recurring concern was keeping "not measured" distinguishable from "measured and flat", because a surface that is smoothly filled in looks better and means less. On a metrology instrument that distinction is the product.

I also made a small, exploratory contribution to a configuration combining two 2D scanners mounted in different planes into a 3D scanner for a medical application, with prosthetics as the intended use. My involvement there was limited, and I present it as such - but it was instructive, because this fixed multi-view design used two sensors as its minimum selected configuration, and with an organic, curved target surface the limiting factor was sensor placement and coverage geometry rather than anything algorithmic.

The status matters for how I describe the whole thing: this was an R&D prototype, not a shipped product. It demonstrated the approach, produced models from real multi-sensor data and gave the company an evidence-based view of the libraries, and the contract ran three months. I would not claim more than that.

What the project did for me was structural. Three months is not long, but it was the first time my algorithm work had to exist as an application somebody else could build and run: a real build system, third-party dependency management, version control, a user interface, and failures that had to be presented rather than printed. Coming from MATLAB, where the data fits in memory and the author is the only user, that is the whole distance between research code and software - and it is why I treated the following sixteen months as a foundation to build deliberately rather than taking the next available role.

## Project Deep Dive 6 - Vehicle Satellite Monitoring Systems (10 Minutes)

This is the earliest part of my career, and I would bring it up when the role involves hardware, field-facing engineering, or simply when someone asks how I learned to debug.

From June 2010 to May 2012 I was an engineer in the navigation and information technologies department of the Belarusian state land-cadastre organization, which operates the national Land Information System. The department delivered GPS and GLONASS vehicle monitoring to fleet operators. I installed and connected around two hundred tracking terminals across more than ten cities, one per vehicle, covering roughly two hundred vehicles including both road and rail units, configured the server side of the monitoring platform for new vehicles and clients, handled equipment acceptance and repair, coordinated procurement with the manufacturers, and trained clients to use the system. I also built the organization's web presence on Joomla and Drupal.

This was field engineering rather than a software role, and I present it that way. I carried out the installations myself, sometimes alone and sometimes as the senior of a pair, alongside server-side configuration, equipment support, client training and the organization's Joomla and Drupal sites.

The craft in an installation is entirely invisible in a specification. Antenna placement has to give the receiver sky visibility through a metal vehicle body that is actively in the way. The mounting has to survive months of vibration. The cable has to be routed away from the electrically noisy parts of a working engine bay. The power connection has to behave correctly when the ignition is off, which is when half of the interesting failures happen. None of that is in a manual, and all of it decides whether the system still works six months later.

Configuration is the other thing I would raise, because it is a failure mode software people recognise instantly. The same logical state lives in two places - on the terminal and on the server - and they have to agree. A vehicle can transmit perfectly and still be invisible on the map, or attributed to the wrong client, because the two sides disagree. From the operator's side that looks identical to a transmission fault, which sends diagnosis in completely the wrong direction.

Client training was more technical than it sounds, and I would defend the time spent on it. An operator who understands that a gap in a track can mean lost cellular coverage, or a vehicle parked underground, reports something useful. One who does not reports "the system is broken". Since the client is the first observer of almost every fault, the quality of every incoming report was set by how well they had been taught. An uncalibrated observer produces unusable observations.

The reason this is still worth mentioning is the shape of the problem. A vehicle monitoring system is a chain of four independent failure domains - satellite signal, the physical installation in the vehicle, the cellular link, and the server - and the operator observes only the far end of it, as a track on a map. There is no stack trace. Diagnosis was elimination: does this affect one vehicle or several, are the affected vehicles geographically clustered, has data stopped entirely or is it arriving late, is the server-side configuration intact. And every investigation had a travel cost attached, so the discipline was to extract the maximum from remotely observable evidence before committing to a trip. That is the same reasoning I now apply to logs and captures before attaching a debugger.

One more detail about the deployment gives the right sense of scale: around two hundred terminals across more than ten cities, one per vehicle, on road and rail units, over two years - installed, connected, accepted into the monitoring system and then kept working. Deployment there was literal. A release meant a vehicle back in service with its terminal working and its configuration correct on the server, and the client was paying for every hour the vehicle was not earning.

Two lessons from it stayed. One is that an acceptance check confirms a state, not a condition: equipment that passes at handover is not equipment that will survive months in a vibrating, electrically noisy vehicle, and marginal installations fail weeks later with nothing pointing back at the cause. The other is the difference between missing data and wrong data. Missing data announces itself. A plausible but incorrect track does not, and the operator keeps making decisions on it.

Then from October to December 2012, part-time alongside my new job at PELENG, I worked at SKB Kamerton, a manufacturer of this class of equipment, maintaining their C#-based vehicle tracking software and debugging issues that ran into its MySQL and PostgreSQL storage. That was my first commercial software maintenance work, and it was the same domain approached from the code end rather than the vehicle end - including the same recurring question of whether a defect belonged to the application logic or to the data layer. Tracking data is high-volume, time-ordered and queried by time and vehicle, so a fault in the application and a fault in storage or retrieval look almost identical to the user: data that is wrong, slow or missing. I would reproduce the behavior, then follow the affected data from the application's request through to what the database actually held and returned, rather than assuming the layer that reported the symptom was the layer that owned it. Years later, tracing a value from C++ through persistence into what a user sees is the same method with different tools.

If I had to name what this whole period gave me, it is that a system's real behavior is not what its documentation says, and the difference shows up in the field rather than on a bench. Everything since - flight tests, on-device debugging on a phone, production failures in a decades-old C codebase - has been a variation on that.

## Project Deep Dive 7 - The 2020-2021 Transition (10 Minutes)

If the question is about the sixteen months between RIFTEK and EPAM, this is the answer, and it is a deliberate period rather than a gap.

RIFTEK ended in May 2020 after three months. That had been my first commercial C++ work and it confirmed the direction, but three months is not a foundation, and I came from MATLAB, where I could assume the data fitted in memory, that I was the only person who would run the program, and that a failure meant a message in the console. None of that survives contact with software someone else installs. So instead of taking the first available role I spent the following sixteen months closing that distance on purpose.

The structured part was EPAM's C++ mentoring programme, from May 2020 to September 2021 - one to one with an assigned EPAM engineer and regular scheduled meetings, so my code and my decisions were reviewed against a commercial standard - with their C++ laboratory running from March to September 2021. No certificate was issued for either; the record is the work.

The practical part was my own. I built a desktop personal-finance application in C++20 from nothing, and it is public on GitHub at about three hundred commits. The structure is four layers, each its own library: domain models at the bottom, a data-access layer above them, a single business-logic facade, and an FLTK interface on top. The data-access layer is two tiers - a class per entity writing prepared SQL against the SQLite C API, and a repository class per entity above it, over a shared manager that owns the connection. The schema is eight tables, and the transaction table carries fifteen columns with foreign keys into seven of the others. Logging through plog sits where failures actually originate, in that data layer: the database being opened, each insert and lookup, and the SQL error text when a statement fails. Alongside the application I worked through Stroustrup's *Programming: Principles and Practice*, second edition, and published the exercises as their own repository.

The domain looks unremarkable and has one genuinely tricky rule in it. Each account holds its own currency, with a single base currency behind all of them, so every amount is converted for balances and reporting, and a transfer between two accounts has to apply the rate adjustment and leave both balances correct. Nothing announces a fault there - the figures still look like money and the totals still render - so an error appears only as a balance that quietly disagrees with reality.

I would also say what the code shows about how I was thinking at the time. The layer directories are numbered, so the intended direction of dependency is visible in the layout; but the executable links all four targets flat, so nothing in the build actually prevents a shortcut from the interface into storage. Naming the layers made the discipline easy to keep. Making the link graph refuse the shortcut is what I would do now. There is a second loose end of the same kind: after writing the binding by hand for eight entities I decided an ORM would remove most of it, added one as a submodule, and never carried the migration through. It is still in the build, unused. If an interviewer opens the repository and asks, the honest answer is that it is unfinished work left visible, and the right fix is to finish it or remove it rather than explain it.

The mentoring deserves a word on format, since there is no certificate behind it. It was one to one with an assigned EPAM engineer and regular scheduled meetings across the full sixteen months - my code and my design decisions reviewed by someone working to a commercial standard, at an interval short enough that a habit got caught rather than compounded. That is the specific thing a personal project cannot supply, because working alone nothing corrects a habit that feels fine to the person who has it.

Two things came out of it that I still use. Adopting tests from the first feature rather than after the design settled changed what got built, not just what got verified - anything awkward to test was a component doing too much, and working alone that signal is the closest thing to a reviewer. And the honest lesson is the coverage I did not write: I tested the simple model types and left the multi-currency transfer arithmetic untested, which is the one place in that application where an error is silent. The effort went where testing was easy rather than where being wrong was dangerous, and noticing that afterwards was worth more than the tests I wrote.

What I would want an interviewer to take from the period is not the application - it is the shape of the decision. I could have taken the next available role in May 2020 with three months of commercial C++ behind me and learned on someone else's project. Instead I spent sixteen months without income building the foundation, with an external programme setting the standard and my own project giving the work somewhere to land. Neither half would have worked alone: a personal project without review drifts, and a programme without a project stays theoretical.

If the question is what specifically changed, it is the things research code never requires. Memory and object lifetime, where my MATLAB instincts were not wrong so much as absent. Failure handling for a user who cannot be asked to reproduce anything. A build that works from a clean checkout on a machine that is not mine. Tests that exist before the design has settled, because that is when they still change what gets built. Those are the four things I did not have in March 2020 and did have by September 2021, and every commercial project since has used all of them.

EPAM hired me in September 2021, at the end of the programme.
