# Embedded SIP Desk Phone Platform | May 2025 - August 2026

## 01 Project Overview

I worked on the software stack for an embedded SIP/IP desk phone platform developed for Cuman / Digital System Servis (DSS). I was on the project from May 2025 through August 2026. The product targeted managed business telephony environments where organizations need physical desk phones with SIP accounts, extension dialing, BLF and speed-dial keys, local and remote contacts, diagnostics, audio/video calling, web-based administration, and centralized provisioning.

This was a device software stack, not a standalone application. The system included a C++/Qt embedded phone application, a customized Linphone SDK/liblinphone layer, Yocto-based Embedded Linux integration, a Windows Autoprovisioning Manager, device-side runtime services, firmware packaging, and integration with the phone's built-in web configuration interface.

The phones supported SIP URI dialing, internal extension dialing, direct IP calls, and regular numeric dialing through configured SIP infrastructure. Numeric destinations were converted into SIP calls and routed by external PBX/SIP-provider infrastructure. The devices did not implement a direct PSTN gateway, analog telephony interface, or carrier routing layer. Calls to the public telephone network were possible only when the connected PBX, SIP provider, or SIP trunk provided PSTN breakout and a matching dial plan.

Each phone also had a browser-accessible configuration interface. I did not implement that web frontend or the device-local REST/API layer used by management/configuration flows; those were handled by another developer. My work had to remain compatible with them through firmware packaging, local web-server/runtime configuration, persistent settings, provisioning files, HTTPS/certificate setup, existing settings/API endpoints, and coexistence with the main Qt phone application across firmware updates and managed deployments.

## 05 Development Process

The workflow was lightweight and direct:

- Asana for task and bug tracking.
- Telegram for daily cross-team communication.
- GitLab for source control.
- Physical phones for integration and regression testing.
- Manual and semi-automated builds for firmware/application validation.

Automated CI/CD did not provide full firmware or on-device regression validation. There was build automation in the repository, but the practical validation path for most changes was still developer-driven: build the relevant component, deploy it to a physical phone or firmware image, and reproduce the original scenario on hardware.

Most incoming work consisted of bugs reported by the customer or discovered during device testing. Tasks were tracked with the available symptoms, reproduction notes, logs, firmware version, device model, SIP/PBX configuration and provisioning state. In the early phase, some reports were incomplete, so part of the engineering work was reconstructing the failing environment from partial evidence. As the project matured, QA reports became more structured and usually included debug-level logs and more precise reproduction steps.

The useful first step was usually classification, not coding: decide whether the symptom looked like provisioning generation, Qt model state, SDK behavior, Linux runtime setup, network/SIP infrastructure, media-device behavior or a mismatch between configuration entry points. That reduced the chance of fixing a visible symptom while leaving the real cross-layer cause untouched.

The work was therefore not just "fix an isolated bug in the UI". A customer-visible problem could originate in generated provisioning data, Linphone account state, SIP authentication, Linux network configuration, service startup order, media-device availability, filesystem layout, or a mismatch between web configuration and Qt application state. Debugging required following the state across these layers and validating the final behavior on the phone.

This mattered especially for:

- Embedded Linux image changes.
- Linphone SDK changes.
- Provisioning behavior.
- Network and TLS/certificate setup.
- Audio/video device behavior.
- Web UI coexistence with the Qt application.
- Hardware-dependent features such as buttons, USB devices, display behavior, camera, audio routes and network interfaces.

Testing was strongly scenario-based. A typical bug report included a specific device state, SIP account configuration, PBX behavior, network topology, provisioning template, firmware version, and steps that had to be repeated on the target phone.

The typical investigation loop was:

- Review the task, attached logs and customer notes.
- Recreate SIP accounts, provisioning data and network conditions where required.
- Build the relevant component or firmware image.
- Deploy the build to a physical ARM64 phone.
- Reproduce the issue using the original call, provisioning or startup sequence.
- Collect application logs, SIP logs, system logs, media statistics and generated configuration.
- Compare generated provisioning configuration with effective runtime configuration.
- Use Qt Creator remote debugging, gdb/gdbserver or additional diagnostics when needed.
- Patch or coordinate the fix in the relevant layer and repeat the original scenario on hardware.

The feedback loop was longer than ordinary desktop development, but that was the cost of validating a real embedded product. Many defects only appeared when the device, SIP server, provisioning files, display stack, audio/video hardware and embedded Linux runtime were combined.

### Architecture and Orchestration

The codebase's central runtime object was CoreManager. I worked mainly on the Qt application side around Linphone integration, MVC/MVVM-style models, account settings, call list/session models, contacts models, contact import pipeline, SIP address/status models, BLF subscription management, GPIO integration, audio behavior, network state and UI-facing controllers. CoreManager also handled or routed important SDK and device events: registration state changes, call state changes, call statistics, provisioning state, network reachability changes and BLF notifications. This made it the main bridge between asynchronous lower-level events and the rest of the Qt application.

The call UI was organized around controller-based flow rather than direct UI-to-SDK manipulation. Components such as CallSessionManager, AudioCallController, VideoCallController, AudioConferenceController and VideoWindowController helped separate call state, media state, conference behavior and rendering behavior from the widgets themselves. This made the code easier to debug when call transitions happened asynchronously or in quick succession.

In practice, the architecture was not a pure textbook MVC or MVVM implementation. It was a Qt application with MVC/MVVM-style separation where models represented SIP accounts, calls, contacts, settings and runtime state; controllers translated user actions and asynchronous SDK callbacks; and widgets focused on rendering and user interaction. The accurate description is MVC/MVVM-style separation rather than a claim of a perfect framework-pattern implementation.

### Primary / Backup SIP Server Behavior

One major area I implemented was project-specific registration behavior for primary and backup SIP servers.

This included the Linphone-side backup-server behavior, registration watchdog logic, failover/failback control, authentication synchronization and the Qt/provisioning integration needed to keep the same behavior visible and configurable consistently. This should still be described as work in the product's customized Linphone/liblinphone layer, not as ownership of upstream Linphone.

The product requirement covered:

- Primary SIP server configuration.
- Backup SIP server configuration.
- Automatic failover when the primary server became unavailable.
- Controlled failback when the primary server became available again.
- SIP registration watchdog behavior.
- Authentication data synchronization between primary and backup server contexts.
- Runtime visibility into which server was currently active.
- Persistence of active-server state and related metadata.

Meeting that requirement touched Linphone account/proxy configuration, registration state handling, configuration persistence and public C API exposure.

The failover feature was not only an application-level retry loop. The SDK had to know which server was currently active, whether the account was registered through the backup server, when a switch had happened, and when another switch or failback attempt was allowed. The application and provisioning tool then had to consume the same model so that UI state, generated configuration and runtime SDK behavior did not diverge.

In the integrated codebase, this involved SDK-level accessors and configuration paths for primary server address, backup server address, active server address, backup-server state, failback attempts and authentication synchronization. Without that model, the application could display a configured backup server while the SDK internally continued using stale registration or authentication state.

Examples of SDK-level concepts and data involved:

- Primary server address.
- Backup server address.
- Active server address.
- "currently on backup server" state.
- Registration watchdog enablement and intervals.
- Switch cooldown.
- Failback timing.
- Last switch timestamp.
- Primary/backup realm handling.
- Synchronization of authentication info with the active server.
- Forced failback attempts.

### Authentication and Realm Handling

The project had non-trivial SIP authentication requirements because real PBX/SIP-server deployments did not always behave identically.

I worked on behavior around:

- Strict authentication lookup.
- Realm-specific authentication.
- Primary and backup realms.
- Digest authentication data reuse where safe.
- Handling 401/407 authentication challenges.
- Avoiding incorrect credential use across server contexts.
- Keeping registration failover compatible with authentication state.

The most fragile scenarios involved HA1 or realm-specific credentials. HA1 values are valid only for the realm used to calculate them, so they cannot be blindly reused if primary and backup servers present different authentication realms. The SDK and provisioning logic had to avoid a state where registration moved to another server but continued using credentials that belonged to the previous realm or identity.

The platform integrated:

- Device web/runtime components.

### Why Yocto

Within that inherited constraint, Yocto was still the right fit because this was a reproducible embedded product image, not a regular Linux workstation or a single application package. The firmware had to combine the NXP/i.MX board-support stack, custom kernel/U-Boot changes, Qt/Wayland, the customized Linphone SDK, media libraries, WebRTC/mediasoup dependencies, web configuration files, runtime scripts, default configuration, certificates, fonts, sounds and model-specific files into one controlled filesystem image.

The important engineering constraint was control: exact dependency versions, sysroot/toolchain behavior, package metadata, installed paths, startup order, runtime services and update behavior all had to be reproducible. A missing file in the image, wrong RPATH, wrong pkg-config metadata, broken service dependency or incorrectly installed default archive could make a feature fail only after flashing the complete firmware.

For accuracy, this should be described as the rationale for continuing to work inside the project's inherited embedded build system, not as a claim that I personally selected Yocto or that our team replatformed the firmware stack. My work was on using and adapting the Yocto-based platform for application, SDK, runtime-service and firmware-image integration.

Other approaches would solve only part of the problem:

- Plain Qt deployment or copying binaries over SSH would be useful for quick debugging, but it would not define the complete root filesystem, service startup, default configuration, web files, certificates, kernel/U-Boot changes, update scripts or factory image content.
- A Debian-like embedded root filesystem would be faster for prototyping, but it would give less control over BSP integration, exact dependency versions, image contents, package metadata and reproducible firmware assembly.
- Buildroot would be simpler for a small image, but this product needed a layered vendor/customer BSP model, package metadata, generated SDK/sysroot support, model-specific recipes and long-term maintainability for a stack containing Qt, Linphone SDK, WebRTC, mediasoup libraries, local web services and hardware-specific runtime components.
- A Docker or standalone cross-compilation setup could help build individual components, but it would not describe the final target image or guarantee that the installed files, services and runtime dependencies matched the device firmware.

Yocto was therefore the practical choice because it let the product keep board-support code, application recipes, SDK integration, runtime services, model-specific differences and firmware packaging under one build system.

This required bridging external build systems with Yocto sysroots, package metadata, native build tools and target filesystem packaging.

Startup order was a real product concern. The phone application depended on the compositor, filesystem layout, media devices, scripts and local services being ready. ## 09 Autoprovisioning Manager

I also worked on, and largely built out, the Windows Autoprovisioning Manager used by installers and IT administrators to discover, configure and provision fleets of Cuman ITL78x phones.

A foundation for the tool already existed when I joined. My work was to finish the application and implement most of the practical provisioning and support functionality on top of that foundation: device discovery, provisioning generation and distribution, project save/load, SIP/HA1 handling, backup-server configuration, DHCP/TFTP workflows, installer packaging, localization and diagnostics-related support flows.

The tool automated tasks that would otherwise require manual configuration on each phone.

Its main goal was to turn manual per-device setup into a repeatable provisioning workflow. Each phone had many parameters that had to be generated consistently: SIP server, backup SIP server, transport, SIP identity, authentication credentials, realm, HA1 hash, BLF targets, contacts, network settings, timezone/NTP-related values, UI preferences and device-specific files.

Manual configuration was risky because a small syntax or data mismatch could break a runtime feature. For example, an incorrect SIP URI, wrong realm, invalid HA1 value, wrong route, broken backup-server field or malformed BLF target could later appear on the phone as a registration failure, failed failover, broken speed dial or incorrect phone-number routing.

### Main Features

- Device discovery over the local network.
- ICMP and UDP discovery flows.
- SNMP-based device querying.
- DHCP option 66/67 provisioning support.
- Built-in TFTP distribution of provisioning files.
- SIP account configuration.
- Backup SIP server configuration.
- Optional configuration of up to 10 SIP accounts in the current project/tooling scope.
- Device network settings.
- Web/admin credentials and password hashing where required by the device configuration format.
- Template-based configuration generation.
- ZIP archive packaging.
- SQLite persistence.
- Localized UI resources.
- Silent installer support.

### .NET 8 Migration

I worked on migrating and modernizing the Windows tool from a legacy .NET Framework 4.8-style codebase to .NET 8 for Windows.

The .NET/WinForms foundation was inherited, not selected by me or by our team. My work was modernization and feature development within that existing desktop-tool stack.

This included:

- Moving to SDK-style project structure.
- Updating NuGet package references.
- Preserving App.config and userSettings compatibility where needed.
- Updating Windows-specific dependencies.
- Keeping WinForms behavior stable.
- Updating test projects.
- Ensuring generated provisioning files remained compatible with the phones.

The concrete migration breakage was saved `.cuman` project state/restore compatibility. The WinForms UI itself did not need to be redesigned. Generated provisioning output was a regression surface that had to stay stable, not a separate case where all generated formats broke during migration.

The tool used `.cuman` project files to save and restore the administrator's work: selected device options, SIP account data, backup server fields, BLF button state, remote contacts settings, wallpaper/ringtone choices, backlight, microphone-state behavior and other UI-driven configuration. During modernization, the old generic "save controls from tabs/panels" approach was too fragile. It was easy for a new UI field, changed control name, DataGridView value or changed serialization behavior to break project restore or silently drop part of the saved state.

The fix was to make project save/load more explicit. The code now uses a dedicated `Project` model with nested `SipAccountUIState` and `BlfButtonState` data, serializes that state as JSON, encrypts it in the `.cuman` file, and restores the UI through explicit `GatherUIState` / `RestoreUIFromState` logic instead of relying only on generic control-tree serialization. This made the saved project format easier to reason about when new fields were added.

Several later changes had to be checked against this project-file format: moving the provisioning tool from the original 5-account assumption to the project decision to support 10 SIP accounts in the current internal build scope, adding Password/HA1 authentication mode, adding screen backlight, saving microphone-off state and changing remote-contact update interval semantics. The 10-account point should be treated as project/tooling scope, not as a public product-spec claim. The important compatibility risk was that an old or partially saved project could open with missing/default values, or a new field could be present in the UI but absent from the saved `.cuman` file.

Generated provisioning output had to remain compatible as well. Even where generated config itself did not break during the migration, the migration and later fixes still had to preserve details such as `config.conf` keys, `server_backup`, `reg_proxy`, `reg_identity`, `reg_route`, `auth_info` sections, `passwd`/`ha1` handling, domain-without-port rules, TLS port behavior, BLF file generation, MAC-specific archive names and ZIP archive layout. A small difference in escaping, file naming, archive structure, default value or hash generation could become a device-side SIP/provisioning bug.

### SIP Digest and HA1 Handling

The provisioning tool supported SIP Digest authentication workflows needed for SIP account provisioning.

This included:

- SIP REGISTER probing.
- 401/407 challenge handling.
- WWW-Authenticate and Proxy-Authenticate parsing.
- Header folding handling.
- Realm auto-discovery.
- HA1 generation.
- MD5-based digest fields required by the device configuration.
- Separate handling of primary and backup SIP server configuration where required.

HA1 is calculated as MD5(username:realm:password). That made realm detection a critical part of provisioning, especially when the same account could be used with primary and backup SIP servers. If the realm was detected incorrectly, the generated HA1 value could look syntactically valid but fail during real SIP registration.

The parser had to handle practical differences in SIP authentication challenges: WWW-Authenticate versus Proxy-Authenticate, quoted realm values, bare realm values, different parameter ordering and folded headers. These details mattered because administrators expected the provisioning tool to work against real PBX/SIP-server deployments, not only against one idealized server implementation.

### DHCP / TFTP Provisioning

The provisioning workflow was centered on standard enterprise-style provisioning:

- DHCP option 66/67 to point phones to provisioning resources.
- TFTP delivery of generated configuration files.
- Device-specific file naming and packaging.
- Network-interface selection on Windows.
- Adapter and IP configuration assistance.
- Integration with device-side autoprovisioning behavior.

The generated provisioning output could include common files and MAC-specific files. This made it possible to share base configuration across a fleet while still generating per-device SIP accounts, credentials, BLF layout, contact data and device-specific resources.

The tool also needed useful diagnostics for installers: which local adapter was selected, which address was used for provisioning, whether the phone was discovered, whether the generated file existed, whether TFTP requests arrived, and whether the expected MAC-specific archive was available.

## 10 Complex Engineering Tasks

This section summarizes the main complex engineering areas from the project. The key point is that most work was cross-layer: a visible phone behavior was usually caused by interaction between the Qt application, Linphone SDK, generated provisioning configuration, Yocto runtime setup, network conditions, SIP server behavior and physical hardware constraints.

### 1. Multi-Layer Telephony State Management

A single user-visible call state depended on Qt UI state, Linphone SDK state, SIP signaling, RTP/media state, hardware controls, provisioning settings and persistent account configuration.

The difficult part was keeping these layers synchronized when calls were transferred, upgraded to video, merged into conferences, failed during registration changes, or affected by network changes.

### 2. Primary / Backup SIP Server Failover

The backup-server feature was one of my implementation areas and could not be treated as a simple alternate string in configuration. It required stateful behavior inside the SDK and application:

- Which server is active now?
- Which credentials and realm apply?
- When should the phone switch?
- When should it fail back?
- How should state survive restart?
- How should the UI and provisioning reflect it?

This touched liblinphone account/proxy internals, public APIs, application account models, provisioning templates and real-device validation.

### 3. Embedded Web Configuration Coexistence

The phone had both a native Qt UI and a browser-accessible web configuration interface. I did not implement the web frontend or REST/API layer; another developer owned that work. My part was on the Qt application and MVC/MVVM side: keeping models, settings state, provisioning assumptions, firmware/runtime integration and UI behavior compatible with configuration changes that could also arrive through the web/API path.

The challenge was avoiding inconsistent state between local UI changes, web/API configuration changes and provisioning updates.

### 4. Yocto Image and Runtime Integration

Many bugs were not isolated C++ defects. They appeared only after the application, SDK, runtime services, Weston, web components, configuration files and boot scripts were combined into a firmware image.

Solving these issues required tracing behavior across BitBake recipes, installed files, systemd units, startup scripts, environment variables, target filesystem layout and runtime logs.

### 5. Phone-Side WebRTC / mediasoup Integration on Embedded ARM64

The ITL789-class video-conference path involved native WebRTC-related libraries, mediasoupclient, libsdptransform, libyuv and Qt multimedia rendering on an embedded ARM64 device.

The difficult parts included build reproducibility, ABI compatibility, media-device behavior, video-frame conversion, runtime performance and debugging conference scenarios on the actual device.

### 6. Network Configuration and Provisioning

The phones were intended for managed corporate networks where DHCP, static IP, VLAN, DNS, provisioning servers, SIP servers and certificates had to work together.

Issues in this area often required checking generated provisioning files, phone-side persistent settings, Linux network configuration, application models and user-visible settings screens.

### 7. Authentication and Realm Compatibility

SIP authentication had to work across real PBX and SIP-provider behavior. Realm values, primary/backup server changes, 401/407 responses and stored credentials had to be handled carefully to avoid registration loops, failed failover or incorrect credential reuse.

### 8. Physical Device Debugging

Many issues could not be reproduced on a desktop build. Hardware buttons, audio routes, camera devices, USB behavior, display timing, Wayland startup and network interfaces all required testing on physical phones.

### 9. Migration of Legacy Provisioning Tooling

The Autoprovisioning Manager migration had to modernize the codebase without changing the generated configuration semantics expected by deployed phones.

The risky part was not only compiling under .NET 8; it was preserving administrator workflows and avoiding silent behavior changes in provisioning output, authentication hashes, network behavior, localization and installer behavior. The concrete problem area was saved `.cuman` project behavior: project save/load had to keep SIP accounts, BLF buttons, auth mode, remote-contact settings, backlight, microphone-state settings and other UI-derived configuration in sync with the generated phone configuration.

This required moving away from fragile generic UI-control serialization toward explicit project-state models and restore logic, then checking that newly added fields were actually saved, opened and converted into the expected provisioning output.

### 10. Diagnostics and Supportability

The platform had to be supportable in the field. I worked on features and workflows around logs, device discovery, network diagnostics, SNMP querying, provisioning output inspection, configuration backup/export and reproducible support scenarios.

## 11 Difficult Bugs & Debugging Cases

### SIP Registration Works on Primary Server but Fails After Failover

**Symptom:** The phone registered successfully on the primary SIP server, but registration failed after switching to the backup server.

**Root cause:** The failure was not in basic account configuration. The problem appeared only after failover, when server address, realm and authentication context could differ from the primary registration path.

**Fix:** I analyzed generated provisioning values, liblinphone account/proxy state, stored AuthInfo records, active server state and registration retry behavior. The final behavior had to keep credentials synchronized with the active server without using credentials from the wrong realm or server context.

**Why it was difficult:** The same user-visible symptom could be caused by generated config, SDK auth lookup, realm mismatch, route selection, transport settings or server behavior. The fix had to be validated through real registration/failover scenarios.

### Phone UI Shows Registered State While SDK Is Already Recovering

**Symptom:** The UI could show a registered or stable account state while the SDK had already started retrying, recovering or switching server state.

**Root cause:** Some registration transitions happened quickly, and asynchronous SDK callbacks did not always map cleanly to the current Qt model/UI state.

**Fix:** Debugging required tracing Linphone callbacks, Qt signal delivery, account models, registration-state mapping and UI update timing. The goal was to make the displayed state follow the effective runtime state instead of stale intermediate values.

### Video Call or Conference Starts but Media Does Not Render Correctly

**Symptom:** A video call or conference could be established at the signaling level, but local or remote video did not render correctly.

**Root cause:** The issue could be in camera selection, Qt multimedia routing, native video window lifecycle, libyuv conversion, WebRTC/media pipeline behavior, codec negotiation or target-device runtime dependencies.

**Fix:** These bugs required separating SIP/session success from media-path success, then checking SDK call parameters, negotiated media direction, rendering setup, target image dependencies and logs across several layers.

### Device Boots but Phone Application Starts Before the Runtime Is Ready

**Symptom:** The device booted, but the phone UI failed to start reliably or behaved incorrectly immediately after startup.

**Root cause:** Some boot-time issues came from service ordering rather than application code. Weston, splash behavior, runtime paths, scripts, local services and the Qt application had to start in the correct sequence.

**Fix:** The fix required checking systemd units, Yocto-installed files, startup scripts, Wayland socket availability, runtime dependencies and actual boot logs on the phone.

### Provisioning File Looks Correct but Phone Applies Only Part of It

**Symptom:** The generated provisioning file or archive looked correct on the PC, but the phone applied only part of the configuration.

**Root cause:** Provisioning bugs could come from template generation, file naming, archive contents, TFTP delivery, DHCP option behavior, phone-side parsing, model-specific differences or persistence rules.

**Fix:** Debugging required comparing generated files, network delivery, TFTP requests, phone logs, resulting persistent configuration and the state visible through the Qt UI or web configuration interface.

### Saved `.cuman` Project Opens but Restores Incomplete State

**Symptom:** A saved Autoprovisioning Manager project could open without restoring all expected UI state, or a newly added configuration option could disappear after save/open.

**Root cause:** The project file format had to represent UI-derived configuration, SIP account data, BLF buttons and newer fields such as authentication mode, backlight, microphone-state saving and remote-contact update interval. Generic control-tree serialization was fragile when controls changed, nested data grids were involved or the schema evolved.

**Fix:** I moved project save/load toward explicit project-state objects and explicit `GatherUIState` / `RestoreUIFromState` logic. The validation was not only "the file opens"; it also had to prove that reopening a `.cuman` project still produced the same meaningful provisioning output.

**Why it was difficult:** The bug could remain hidden until a user reopened an older project, generated a new archive and deployed it to a phone. At that point it could look like a SIP, BLF or provisioning problem even though the real issue was lost or defaulted state in the saved project.

### Network Settings Persist in UI but Not After Reboot

**Symptom:** Network settings appeared to apply in the UI, but were lost or changed after reboot.

**Root cause:** Network settings touched Qt models, validation logic, generated/persistent files, system-level network configuration and service restart behavior.

**Fix:** The fix required verifying both the immediate runtime network state and the configuration that survived reboot. In practice, this meant checking UI state, saved settings, Linux network files, service behavior and the resulting interface configuration.

### BLF State Does Not Match the Monitored Extension

**Symptom:** A BLF key displayed a state that did not match the actual state of the monitored extension.

**Root cause:** BLF issues could involve SIP subscriptions, dialog/presence events, account selection, server behavior, UI model updates and programmable key mapping.

**Fix:** The difficult part was deciding whether the defect was in server notifications, subscription lifecycle, event parsing, state mapping or UI refresh logic. The fix required tracing the full path from configured key target through subscription and event handling to the final UI indicator.

### Autoprovisioning Realm Discovery Fails Against a Specific SIP Server

**Symptom:** Realm discovery worked against one SIP server but failed against another, which later caused invalid HA1 provisioning output.

**Root cause:** Some SIP servers returned authentication challenges with formatting differences such as folded headers, different parameter ordering, quoted/bare realm values or WWW-Authenticate versus Proxy-Authenticate usage.

**Fix:** The fix required making challenge parsing robust enough for real-world SIP servers while keeping generated HA1/auth configuration stable and compatible with the phone firmware.
